We No Longer Own the Code

In recent days, I have stopped trying to understand all the code generated by coding agents. I no longer try to follow every implementation detail or understand every line.

Previously, I wanted to know how everything worked: what each module did, how the modules were connected, and why the code was written in a particular way.

That became unrealistic after I launched four agents working on different tasks simultaneously. They generated a huge amount of code in a very short time. Understanding all of it would have taken longer than generating it.

But this does not mean giving up responsibility.

I am still responsible for:

- the architecture;
- the overall direction of the project;
- whether the result works;
- the documentation;
- the diagrams and charts that explain the system.

Dealing With Agent-Generated Code

The first rule I introduced was simple: agents should generate as little code as possible. More code means more complexity, more maintenance, and more things that nobody fully understands.

The second rule is to plan before coding. Architecture documentation should be created before implementation begins. The agent should understand where the new code belongs, which components it affects, and how it fits into the system.

After implementation, agents should perform thorough testing. Their work should also be reviewed by another agent. Cross-agent code reviews can reveal problems that the original agent missed.

When I need more visibility into a specific part of the system, I can ask an agent to generate a focused diagram for that narrow area. I may not need to understand every line, but I must understand how the important parts interact.

From Vibe Coding to Architecture-Driven Development

Vibe coding is evil. We should stop doing it.

Generating code until something appears to work is not a sustainable development process. The alternative is architecture-driven development.

Architecture-driven development accepts that humans may no longer understand every line of generated code. But humans must still understand how the system works, where responsibilities are located, how data moves through it, and what may break when something changes.

An agent finishes its task, the session ends, and all the rich context inside that session disappears. The code remains, but the reasoning behind it may be lost.

That architectural context must therefore be preserved outside the agent session. It must live in documentation, diagrams, tests, and clearly defined architectural decisions.

It increasingly looks like we, as humans, no longer truly own the code. But we must still own the system.
